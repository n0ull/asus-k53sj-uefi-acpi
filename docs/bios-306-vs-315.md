# BIOS 306 与 315 的离线比较

日期：2026-10-25。用户指出 315 的更新说明为 EC firmware，并提供 306。
本轮仅提取和比较，不刷写、不执行旧版模块。

## 来源与方法

[ASUS 官方 K53SJ 页面](https://www.asus.com/supportonly/k53sj/helpdesk_bios/)：
315（2011/09/25）说明 Update EC firmware；306（2011/07/22）说明修正 S4 测试时
部分光驱自行出仓。页面的简短说明不能作为完整的二进制变更清单。

两个输入都为 2,621,440 字节。306 SHA256：
`fe3610153dba46e4b12f70964e3ea8e9f79086aeec1ce23fbb04ff33ebd93072`；
315 SHA256：`126ee0fa737e35071a4f383b7e1be1579f1e069755bdc6379d96ee3f3b90f8f8`。
306 为用户提供文件，未声称已与独立下载的官方包摘要一致。

使用与此前相同的 UEFIExtract A76，按 FFS GUID 对齐；两边各 188 个 FFS 文件，
GUID 集合没有增删。161 个包含 PE 的文件的完整负载不同，1 个相同；但大量变化
涉及重新构建的时间戳、调试记录和厂商构建路径，不能叫作 161 项功能修改。

脚本：`research/linux/compare-firmware.py`。本地完整结果为忽略目录的
`bios-306-vs-315.json`、`critical-section-hashes.json`、`bios-306-vs-315-ranges.json`。

## 关键模块结果

| 模块 | .text | .data | .reloc | 解释 |
| --- | --- | --- | --- | --- |
| ECProtocol | 完全一致 | 完全一致 | 完全一致 | 当前共享方法表及方法代码的设计已存在于 306 |
| AcpiModeEnable | 完全一致 | 完全一致 | 完全一致 | 当前 +0x38 间接调用路径非 315 新增 |
| SmmBase | 完全一致 | 完全一致 | 完全一致 | 关键 section 无字节变化 |
| SmmDispatcher | 完全一致 | 完全一致 | 完全一致 | 关键 section 无字节变化 |
| Runtime | 不同 | 不同 | 不同 | 存在数据布局变化，进一步检查见下文 |
| PchSmiDispatcher | 不同 | 完全一致 | 不同 | 存在数据引用地址变化，进一步检查见下文 |

ECProtocol 的 .text SHA256 两版均为
`f0b650d162f53f66949469b83a6e58969e2b1ded39453b13430929f919f2f7ed`，
.data 均为 `f102fa5bacd2e8f04e7d769865d3b19ddb09b4f4babb887b836e9f7363825eda`。
其完整 PE 哈希不同，不能用完整哈希差异推导方法代码已变。
上述四个 section 一致的模块，.rdata 仍不同，含构建元数据变化；这不自动等于
每一个 .rdata 字节都只是元数据。

Runtime 与 PchSmiDispatcher 的反汇编指令条数分别为 11,229/11,229 和 3,225/3,225。
去掉 RIP-relative 数据引用位移后，各仍有 6 处非 RIP 数据地址引用差异，其位移均
减少 0x20。对应构建的 data 布局也有 0x20 位移；本轮没有发现新增/删除的控制流。
这是归一化静态比较，不是完整的语义等价证明，不能宣称这两个模块完全一样。

## 确认存在的 DSDT 改动

FFS GUID 11D8AC35-FB8A-44D1-8D09-0B5606D321B9 内的 DSDT 从 56,438 字节变为
56,515 字节。用 ACPICA iasl 20230628 分别反编译，除表头长度、校验与生成说明外，
差异为在 `\_SB.PCI0.GFX0` 新增一个 Serialized `_STA` 方法：

- 当 `0x07D0 < OSYS < 0x07D6` 时，调用 EC0.TSDS 和 PEGR.GFX0.DOFF；
- 返回 0x0F。

同表的 OSYS 赋值将 Windows 2001 系列设为 0x7D1–0x7D3，Windows 2006 为 0x7D6，
Windows 2009 为 0x7D9。因此新增分支针对的是该表识别的早期 Windows 条件，而非
简单的“所有 Windows 都会调用”。不能把操作系统年代名称直接当作实际 OSYS 采样值。
目前没有证据说明此新 _STA 已在 Linux 的 ACPI_ENABLE outb 卡点执行。

另外三个同容器 SSDT 的长度相同；尚未据此宣称它们的内容逐字节一致。
反编译产物和差异在本地忽略目录，不分发原始 ACPI 表。

## EC 固件载荷与 ECProtocol 必须分开

完整镜像的首个 FV 之前区域（0–0x90000）有 19,950 个不同字节；差异的 4KB 块
位于 0x80000–0x83000 和 0x84000–0x8F000。该 64KB 区域是需要继续识别的 EC 载荷
候选，与官方更新说明吻合，但本轮未完成芯片/更新器引用和载荷格式的独立确认，
不将未知 padding 直接定名为完整 EC 固件。仍不能排除控制器内部固件变化影响响应。

## 对当前研究的影响

1. 比较旧版是必要对照。ECProtocol/AcpiModeEnable 的可疑共享表设计不是 315 新增，
   “315 修改这段 x64 方法代码导致问题”的假设被削弱。
2. 不能从此推出 306 也必然失败，或降级就必然成功：EC 控制器载荷、DSDT、构建布局
   仍有变化，真实旧版运行状态未采样；仅替换 BIOS 文件也未必能复现相应 EC 状态。
3. 后续 EC WATCH 与单槽位实验已确认 315 的方法地址转换和触发点，见 [根因证据](root-cause-evidence.md)；这仍不回答故障最早在哪一版固件引入。
